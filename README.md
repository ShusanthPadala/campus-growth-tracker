# Campus Growth Tracker

Registration + campaign dashboard for the (simulated) NxtWave workshop **“Build Your First AI Project in 60 Minutes”** — target **500 registrations in 7 days**.

> Simulated campaign for a product demo. **Not** an official NxtWave page.

**Stack:** Next.js 16 (App Router, TypeScript) · Supabase (Postgres + Auth) · Vercel.

```
Student browser ──HTTPS──▶ Next.js (Vercel)
   /            registration form          │  server-only env: SUPABASE_URL, SUPABASE_ANON_KEY, IP_HASH_SALT
   /api/register ── validates, honeypot, ──┼──▶ Postgres function register_student()   (the ONLY public write path)
                    hashes IP for limits   │        · unique index on normalised email (duplicates, races)
Admin browser ───▶ /admin, CSV export ─────┼──▶ tables via the admin's own session; Row-Level Security = admins only
   /demo        fictional data, in code ───┘        (the demo never touches the database)
```

Browsers never talk to Supabase. There is **no service-role key** anywhere in the app.

## What is real and what is simulated

| Feature | Status |
|---|---|
| Public registration (no login), validation, success/error states | **Real** – saved to Postgres |
| Unique registration per email (case, `+tag`, Gmail-dot variants), safe under simultaneous submits | **Real** – database unique index |
| Referral codes (generated by admins) and source attribution | **Real** |
| Dashboard: totals, progress to 500, sources, referral performance, daily trend, leaderboard | **Real** – from stored records |
| CSV export (registrations, summary) | **Real** – admin only, normal browser download |
| Admin login | **Real** – Supabase Auth, allow-list in `admin_users` |
| **WhatsApp buttons** | **Share links only** (`https://wa.me/?text=…`). They open WhatsApp with a pre-filled message. **No automated messaging, no WhatsApp API.** |
| Confirmation emails / messages | **Not built.** The success screen says so. |
| `/demo` and “Demo data” toggle (306 fictional students) | **Simulated** – generated in code, labelled DEMO DATA, never written to or read from the database |

## 1 · Run locally

Requires Node.js ≥ 20.9.

```bash
npm install
cp .env.example .env.local      # then fill in the values (section 2)
npm run dev                     # http://localhost:3000
```

Without Supabase values the site still builds and `/demo` works; registration returns a clear “not available” message instead of pretending to save.

## 2 · Set up Supabase (free plan)

Click-paths can differ slightly between dashboard versions — follow the labels.

1. **Create a project** at supabase.com (note the database password somewhere safe; the app doesn’t need it).
2. **Create the tables:** *SQL Editor → New query* → paste the whole of `supabase/migrations/20261028000000_init.sql` → **Run**. It should finish with “Success”.
3. **Turn off public sign-ups:** *Authentication → Sign In / Providers* (wording varies) → disable **“Allow new users to sign up”**. Only people you create can ever have an account.
4. **Create your admin user:** *Authentication → Users → Add user → Create new user* → email + a strong password → tick **Auto Confirm User**.
5. **Authorise that user as admin:** *SQL Editor* → paste (with your email) and run:
   ```sql
   insert into public.admin_users (user_id)
   select id from auth.users where email = 'you@example.com'
   on conflict do nothing;
   ```
   (`supabase/seed_admin.sql.example`). A user who is merely signed in is **not** an admin.
6. **Copy two values** from *Project Settings → API* (or *API Keys*):
   - **Project URL** → `SUPABASE_URL`
   - the **anon / publishable** key → `SUPABASE_ANON_KEY`
   - ⚠ **Never** use or paste the `service_role` / secret key. This app doesn’t need it.
7. Strongly recommended: enable **MFA** for your admin account (Supabase Auth supports TOTP).

## 3 · Deploy to Vercel

1. Create a **private** GitHub repository and push this folder:
   ```bash
   git init && git add . && git commit -m "Campus Growth Tracker"
   git branch -M main
   git remote add origin https://github.com/YOUR-USER/campus-growth-tracker.git
   git push -u origin main
   ```
2. vercel.com → **Add New… → Project** → import the repo. Framework preset: **Next.js** (auto-detected). Don’t change build settings.
3. Before clicking Deploy, add **Environment Variables** (Production):

   | Name | Value |
   |---|---|
   | `SUPABASE_URL` | your project URL |
   | `SUPABASE_ANON_KEY` | the anon/publishable key |
   | `IP_HASH_SALT` | any long random string — generate with `openssl rand -hex 32` |
   | `SITE_URL` | leave blank for the first deploy |
   | `ENABLE_PUBLIC_DEMO` | `true` (or `false` to hide `/demo`) |

4. **Deploy.** Then set `SITE_URL` to the URL Vercel gave you (e.g. `https://campus-growth-tracker.vercel.app`) and **Redeploy** (Deployments → ⋯ → Redeploy). This makes referral links use the right address.
5. **Verify** (don’t skip):
   ```bash
   node scripts/smoke.mjs https://YOUR-URL                # read-only checks
   node scripts/smoke.mjs https://YOUR-URL --write        # also saves ONE test student and proves duplicate blocking
   ```
   Delete the test student afterwards (SQL Editor): `delete from public.registrations where email like 'smoke+%@example.invalid';`
6. Sign in at `/admin/login`, set the **campaign start date**, create **ambassadors**, and share their links (`/?ref=CODE`) — each has a WhatsApp **share** button.

### ⚠ Free-plan caveats you should know

- **Vercel Hobby is restricted to personal, non-commercial use** (Vercel’s fair-use rules). If this campaign is run by NxtWave as a company activity rather than as your own personal/portfolio project, Hobby is not the right plan. The app is plain Next.js and can run on any Node-capable host; I have only tested it on Vercel-style `next start`.
- **Supabase Free pauses a project after ~1 week of inactivity** and the site stops working until someone restores it in the dashboard. Registration traffic counts as activity, but check the project is awake before launch and after any quiet week.
- The free database is 500 MB — far more than 500 registrations need.

## 4 · Security model

- **Public visitors can read nothing.** Every table has Row-Level Security; `anon` has no table privileges and no policies. Ambassador codes can’t be enumerated.
- **One public write path:** `register_student()` (SQL, `SECURITY DEFINER`, fixed `search_path`). It validates again, checks consent, applies per-client rate limiting, resolves the referral code, and inserts. Duplicates are rejected by the **unique index on `email_normalized`**, so two simultaneous submissions cannot both succeed.
- **Admins:** Supabase Auth sign-in; every admin page, server action and CSV route calls `getUser()` (validated with Supabase Auth) and then `is_admin()`. The database enforces the same rule independently through RLS, so a bug in the app cannot expose registrations to a non-admin.
- **No secrets in browsers:** all env vars are server-only (no `NEXT_PUBLIC_`). The test-suite scans the built browser bundle for the Supabase URL/key, salt and “service_role”.
- **Abuse controls:** hidden honeypot field; 60 submissions/hour per hashed client key (raw IPs are never stored — only an HMAC); 4 KB body cap; CSV formula-injection neutralised.
- **No local-storage substitutes:** nothing is stored in the browser; all state lives in Postgres.

## 5 · Operating notes

- **Uniqueness rule:** emails are trimmed and lower-cased; `+tag` is removed; dots are removed for `gmail.com`/`googlemail.com`. Change it in the SQL function `normalize_email` (the column is generated, so migrate carefully).
- **Rate limit:** edit `c_limit` in `register_student()`. 60/hour/IP is deliberately generous because a whole college lab can share one public IP.
- **Behind a different host/proxy:** the client key uses `x-real-ip` (set by Vercel). On other hosts make sure your proxy sets a trustworthy `x-real-ip`/`x-forwarded-for`.
- **Emails are not verified.** Anyone can register someone else’s email address. Add email confirmation if that matters.
- **Delete a student / test row:** use the Supabase *Table Editor* or SQL (the app intentionally has no delete button).
- **Rotate a leaked anon key:** Supabase → API settings. The anon key alone cannot read data, but rotate anyway if exposed.

## 6 · Tests

```bash
npm run typecheck
npm run test:unit     # validation, metrics, CSV, demo data, route + page rendering
npm run test:db       # real Postgres: constraints, RLS, concurrency, parity with the prototype
npm run build && npm test   # also runs end-to-end against the built server
```

`test:db` and the end-to-end tests start a throw-away Postgres via `embedded-postgres` (first run downloads binaries). Postgres refuses to run as root, so run tests as a normal user (not `sudo`/root, and not inside a root-only container shell).

**What the automated tests cover:** public registration, duplicate and concurrent submissions, referral attribution, persistence across a server crash/restart, rate limiting, admin-only access (SQL RLS + route/action guards), CSV exports, demo-data separation, no-secrets-in-browser, and the smoke script itself.

**What they cannot cover (needs your live accounts):** real Supabase Auth sign-in and session refresh, real PostgREST, Vercel’s headers. Use `scripts/smoke.mjs` after deploying and sign in once by hand to confirm the admin area.
